# 阶段 9：生产容器化与服务器部署设计

## 1. 目标

将已经完成业务开发的涉案卷烟智能统计系统部署到现有 Linux 服务器，并满足以下要求：

- 服务器通过公网 IP 提供 HTTPS 访问；
- 复用服务器现有 Caddy，不中断已有站点；
- 前端、后端和 MySQL 使用独立 Docker Compose 管理；
- 服务器创建全新业务数据库，仅初始化管理员和卷烟品规；
- MySQL、FastAPI 和内部 Nginx 不直接暴露公网端口；
- 数据库使用命名卷持久化，容器更新和重启不丢失数据；
- 每月自动备份一次数据库，保留最近 12 份；
- 每次版本升级前额外执行一次手工备份；
- 代码经测试和秘密检查后提交 GitHub，服务器按固定 Git 标签部署。

## 2. 已确认约束

- 服务器操作系统为 Debian 11，暂不执行系统升级；
- 服务器为 x86_64、2 核 CPU、约 1.7 GiB 内存和 4 GiB Swap；
- 系统盘 40 GiB，当前剩余约 7.6 GiB；
- 服务器已安装 Docker 和 Docker Compose；
- 现有 Caddy 占用公网 80、443 端口，并承载其他业务；
- 现有 8080 端口已被其他服务占用；
- Web 端暂时向所有公网来源开放；
- 使用公网 IP 证书，不依赖域名；
- 初始管理员账号和密码沿用用户当前指定值，但真实密码不得写入版本文件；
- 不迁移本地扫描批次、扫码流水、导出记录和简道云快照；
- 不使用 Alembic，不执行应用启动时自动 DDL；
- 不删除现有服务器容器、数据库、网络和持久化卷。

## 3. 推荐拓扑

```text
公网客户端
   │ HTTPS 443
   ▼
现有 Caddy 容器
   │ scanner_proxy 外部 Docker 网络
   ▼
scanner-web
   ├─ 提供 Vue 生产静态文件
   └─ /api/ 反向代理到 scanner-api:8000
                         │ scanner_internal 内部网络
                         ▼
                    scanner-api
                         │
                         ▼
                    scanner-mysql
                         │
                         ▼
                 scanner_mysql_data
```

公网只开放 80、443 和现有 SSH 端口。`scanner-web`、`scanner-api` 和 `scanner-mysql` 均不设置宿主机端口映射。

## 4. 容器职责

### 4.1 scanner-web

- 使用 Node 多阶段构建 Vue；
- 生产镜像只保留 Nginx 和编译后的静态文件；
- 处理前端路由回退；
- 将 `/api/` 代理到 `scanner-api:8000`；
- 对登录接口设置轻量限速；
- 设置上传体积、安全响应头和合理超时；
- 连接 `scanner_proxy` 和 `scanner_internal`。

### 4.2 scanner-api

- 使用 Python 3.12 精简镜像；
- 安装 `backend/pyproject.toml` 中的生产依赖；
- 使用 Uvicorn 启动 `app.main:create_app --factory`；
- 只连接 `scanner_internal`；
- 从生产 `.env` 读取数据库、Cookie、允许来源和简道云配置；
- 启动时不执行 DDL，由部署步骤显式运行 `init_db`。

### 4.3 scanner-mysql

- 使用 MySQL 8.4；
- 只连接 `scanner_internal`；
- 不映射宿主机 3306；
- 使用 `scanner_mysql_data` 命名卷；
- 配置健康检查、`utf8mb4` 和中国时区显示约定；
- 数据库时间继续按应用约定保存 UTC。

## 5. Docker 网络

### 5.1 scanner_proxy

独立创建为外部网络，现有 Caddy 和 `scanner-web` 加入该网络。Caddy 通过容器名访问 `scanner-web:80`，不依赖宿主机回环地址，也不占用现有 8080 端口。

### 5.2 scanner_internal

由生产 Compose 创建为内部网络，仅 `scanner-web`、`scanner-api` 和 `scanner-mysql` 使用。数据库和 API 无法从公网直接访问。

## 6. Caddy 与 HTTPS

现有 Caddyfile 只追加一个公网 IP 站点，不修改已有三个站点的路由。新增站点执行以下逻辑：

- 使用 Let’s Encrypt `shortlived` 配置申请公网 IP 证书；
- 证书有效期较短，由 Caddy 自动续期；
- HTTP 自动跳转 HTTPS；
- 反向代理到 `scanner-web:80`；
- 保留真实客户端地址和标准转发头；
- 修改前备份 Caddyfile；
- 修改后先执行 `caddy validate`，通过后再执行平滑 `caddy reload`；
- 若证书申请或路由验证失败，立即恢复原 Caddyfile，不重启其他业务容器。

真实公网 IP 只写入服务器 Caddyfile，不写入 Git 版本文件。

## 7. 生产配置与秘密

仓库只提交 `.env.production.example`，其中所有密码和外部接口鉴权值为空。服务器真实配置保存在：

```text
/opt/scanner/config/.env
```

文件权限为仅 root 可读写。生产配置至少包含：

- `APP_ENV=production`；
- `COOKIE_SECURE=true`；
- 生产数据库名、用户和随机数据库密码；
- 生产 `DATABASE_URL`；
- 公网 HTTPS 来源；
- 简道云接口地址、应用 ID、表单 ID 和 API Key。

真实 `.env`、管理员密码、数据库密码、简道云 Token、服务器 IP 和 SSH 参数不得提交 GitHub、写入镜像或输出到日志。

## 8. 发布方式

### 8.1 本地发布准备

1. 整理阶段 5～8 的未提交代码；
2. 检查 `.env`、数据库、备份、导出、日志和生成文件均被忽略；
3. 运行后端全量测试和 Ruff；
4. 运行前端单元测试、ESLint、生产构建和 Playwright；
5. 校验生产 Compose；
6. 执行秘密扫描；
7. 经用户确认后提交并推送 GitHub；
8. 创建不可变发布标签 `v1.0.0`。

### 8.2 服务器部署

服务器将仓库克隆到 `/opt/scanner/app`，检出固定发布标签后构建镜像。首次构建前，只清理已确认无用的 Docker 构建缓存和过期 systemd 日志，不执行带卷删除的清理命令。

服务器资源较小，Dockerfile 必须采用多阶段构建并避免保留 Node、编译缓存和 Python 构建依赖。构建完成后可单独清理本项目产生的无用构建缓存，但不得删除运行中容器使用的镜像。

## 9. 数据初始化

生产数据库使用全新命名卷，初始化顺序固定为：

```text
启动 scanner-mysql
→ 等待健康检查
→ 显式运行 init_db 创建缺失表
→ 创建初始管理员
→ 导入经过校验的 cigarette_products 品规数据
→ 核对管理员和品规数量
→ 启动 scanner-api 和 scanner-web
```

品规迁移使用单独生成的、可审查的初始化数据文件，只包含 `cigarette_products` 所需字段。不得包含本地用户、批次、流水、导出、简道云快照或其他业务记录。

初始化过程必须幂等或明确拒绝重复导入，防止重复创建管理员和品规。

## 10. 资源与日志

针对 2 核、约 1.7 GiB 内存服务器：

- FastAPI 初始使用 1 个 Uvicorn worker；
- MySQL 使用适合小内存服务器的缓冲区配置；
- 容器设置合理内存限制和自动重启策略；
- 保留现有 4 GiB Swap；
- 所有新容器使用 `json-file` 日志轮转，单文件最大 10 MiB，最多保留 3 个；
- 部署前将 systemd journal 控制到约 500 MiB；
- 部署前回收无用 Docker 构建缓存，但不删除镜像卷。

## 11. 安全控制

- 阿里云安全组只开放 80、443 和现有 SSH 端口；
- MySQL、API 和内部 Web 端口不对宿主机映射；
- 登录接口在内部 Nginx 设置限速和突发上限；
- Cookie 启用 Secure、HttpOnly 和 SameSite；
- 后端允许来源仅配置生产 HTTPS 地址；
- 前端不保存密码、Token 或正式业务数据；
- 简道云密钥只存在于后端环境；
- 上传文件继续执行类型、扩展名和大小检查；
- SSH 后续应迁移到密钥登录并限制 root 密码登录；
- Debian 11 已结束官方 LTS，用户接受暂不升级的风险；部署记录中保留该风险项。

## 12. 备份与恢复

### 12.1 自动备份

- 每月 1 日凌晨执行一次 MySQL 逻辑备份；
- 文件名包含数据库名和完整时间；
- 使用 gzip 压缩；
- 保存在 `/opt/scanner/backups`；
- 保留最近 12 份月度备份，超出后删除最旧备份；
- 备份脚本失败时写入系统日志，禁止静默失败。

### 12.2 升级前备份

每次更新 Git 标签或执行数据库结构 SQL 前，必须额外生成一份手工备份并校验文件非空。

### 12.3 恢复验证

恢复时只恢复到隔离测试数据库，确认表数量、管理员、品规和抽样业务数据正确后，才能用于正式恢复。恢复操作不得覆盖正在运行的正式数据库，除非用户明确批准停机恢复。

## 13. 上线步骤

1. 本地完成容器化文件和测试；
2. 用户审查 Git diff 和秘密扫描结果；
3. 用户批准后提交、推送并创建发布标签；
4. 服务器清理已批准的构建缓存和过期日志；
5. 创建 `/opt/scanner` 目录、生产 `.env` 和 Docker 网络；
6. 克隆 GitHub 并检出固定标签；
7. 构建生产镜像；
8. 启动 MySQL 并初始化数据库；
9. 创建管理员并导入品规；
10. 启动 API 和 Web；
11. 在容器内部完成健康检查；
12. 备份、校验并平滑更新 Caddyfile；
13. 验证公网 IP HTTPS 证书；
14. 执行完整业务验收；
15. 重启新系统容器并验证数据持久化；
16. 创建首次部署备份并记录版本。

## 14. 验收标准

- 生产 Compose 配置校验通过；
- 前端、后端和数据库健康；
- 公网 IP 可通过可信 HTTPS 访问，HTTP 自动跳转；
- 现有 Caddy站点和容器不受影响；
- 公网无法访问 MySQL、API 和内部 Web 端口；
- 管理员可以登录；
- 服务器品规数量与本地导出数量一致；
- 新建批次、扫码、调整、来源拆分、完成和 Excel 导出正常；
- 简道云一键导入正常且不会重复创建；
- 容器重启后业务数据和导入状态仍存在；
- 月度备份脚本可生成非空压缩备份；
- 回滚到上一 Git 标签时不删除 MySQL 命名卷；
- GitHub 不包含真实秘密、服务器配置、数据库或备份文件。

## 15. 回滚方案

- 应用回滚：检出上一个发布标签，重新构建并启动 `scanner-web` 和 `scanner-api`；
- Caddy回滚：恢复修改前备份并执行验证和平滑 reload；
- 数据库回滚：默认不回滚数据库，不删除 `scanner_mysql_data`；
- 数据结构不兼容时，先停写并取得用户明确批准，再使用升级前备份恢复；
- 禁止执行 `docker compose down -v`、`docker system prune --volumes` 或删除生产命名卷。

## 16. 范围外事项

- 本阶段不升级 Debian 11；
- 不迁移本地历史业务数据；
- 不改造服务器已有 Caddy、PostgreSQL、Redis 和其他业务容器；
- 不引入 Kubernetes、Redis、消息队列或外部托管数据库；
- 不建设高可用集群、异地容灾或自动发布流水线；
- 不在未经批准的情况下提交 Git、推送 GitHub、清理服务器或连接服务器执行部署。
