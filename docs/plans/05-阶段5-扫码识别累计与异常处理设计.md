# 阶段 5：扫码识别、累计与异常处理设计

**设计日期：** 2026-08-27
**状态：** 已实施并通过验证
**对应需求：** PRD `FR-SCAN-001` 至 `FR-SCAN-008`、`FR-EXCEPTION-001` 至 `FR-EXCEPTION-005`，SPEC `5.6`、`5.7`、`7.2`、`8`

## 1. 目标与边界

本阶段完成“进入进行中批次—连续扫码—自动识别—实时累计—查看异常—解决歧义”的闭环。正式数量和异常状态全部保存在 MySQL，前端只展示后端返回的权威结果。

本阶段同时落实已经批准但尚未进入代码的批次权限收紧与列表关键词检索。权限收紧是扫码写接口的安全前置条件；列表检索只接入批次编号、立案编号和地点，不增加高级筛选。

本阶段不实现人工调整、完成批次、Excel 导出、罚没烟快照、未识别编码人工绑定、事件修改或删除。

## 2. 方案选择

歧义处理采用“保留原事件并追加解决事件”的方案：

- 原始扫码写入 `SCAN / AMBIGUOUS`；
- 选择候选品规后追加 `RESOLVE / SUCCESS`；
- `RESOLVE.source_event_id` 指向原歧义事件；
- `source_event_id` 使用唯一约束，数据库保证同一歧义事件最多成功解决一次；
- 不修改原事件，满足 `scan_events` 只追加规则；
- 不增加独立异常表，保持轻量单体结构。

未识别编码只记录 `UNKNOWN`，本阶段不允许人工指定品规。管理员补充品规后，操作员使用新的 `request_id` 重新扫描。

## 3. 数据库设计

### 3.1 `scan_events`

| 字段 | MySQL 类型 | 约束与含义 |
|---|---|---|
| `id` | BIGINT UNSIGNED | 主键、自增 |
| `request_id` | CHAR(36) | 全局唯一幂等请求号 |
| `session_id` | BIGINT UNSIGNED | 外键 `scan_sessions.id`，RESTRICT |
| `event_type` | VARCHAR(24) | `SCAN`、`RESOLVE`；`ADJUST` 留给阶段 6 |
| `result` | VARCHAR(24) | `SUCCESS`、`UNKNOWN`、`AMBIGUOUS` |
| `raw_code` | VARCHAR(64) | 原始编码；阶段 5 必填 |
| `product_id` | BIGINT UNSIGNED | 外键 `cigarette_products.id`，未知或歧义时为空 |
| `unit_type` | VARCHAR(16) | `CARTON`、`PACK`；未计数时为空 |
| `delta_sticks` | INT | 本次增加支数；未知和未解决歧义为 0 |
| `source_event_id` | BIGINT UNSIGNED | RESOLVE 指向原 AMBIGUOUS 事件，其他事件为空 |
| `reason` | VARCHAR(500) | 阶段 5 为空，阶段 6 调整使用 |
| `candidate_snapshot` | JSON | 歧义候选快照数组，其他结果为空 |
| `product_snapshot` | JSON | 成功计数时的品规快照，其他结果为空 |
| `operator_id` | BIGINT UNSIGNED | 外键 `users.id`，实际操作人 |
| `created_at` | DATETIME(6) | UTC 创建时间 |

约束和索引：

- `UNIQUE(request_id)`；
- `UNIQUE(source_event_id)`；MySQL 允许多个 `NULL`；
- `INDEX idx_scan_events_session_created(session_id, created_at, id)`；
- `INDEX idx_scan_events_session_result(session_id, result, created_at)`；
- 检查事件类型和结果枚举值；`delta_sticks` 保持有符号整数，为阶段 6 的减少调整预留，阶段 5 业务只写正数或 0；
- 表使用 InnoDB、`utf8mb4_0900_ai_ci`。

### 3.2 `scan_session_items`

| 字段 | MySQL 类型 | 约束与含义 |
|---|---|---|
| `id` | BIGINT UNSIGNED | 主键、自增 |
| `session_id` | BIGINT UNSIGNED | 外键 `scan_sessions.id`，RESTRICT |
| `product_id` | BIGINT UNSIGNED | 外键 `cigarette_products.id`，RESTRICT |
| `carton_count` | INT UNSIGNED | 条码成功次数 |
| `pack_count` | INT UNSIGNED | 包码及歧义解决成功次数 |
| `manual_delta_sticks` | INT | 阶段 5 固定为 0 |
| `total_sticks` | INT UNSIGNED | 当前权威总支数 |
| `product_snapshot` | JSON | 首次计数时的品规快照 |
| `updated_at` | DATETIME(6) | UTC 更新时间 |

约束和索引：

- `UNIQUE(session_id, product_id)`；
- `INDEX idx_scan_items_session_updated(session_id, updated_at)`；
- 条数、包数和总支数不得小于 0；
- 表使用 InnoDB、`utf8mb4_0900_ai_ci`。

### 3.3 品规快照

快照固定包含：`product_id`、`carton_code`、`pack_code`、`brand`、`standard_name`、`carton_retail_price`、`sticks_per_pack`、`packs_per_carton`、`sticks_per_carton`。金额在 JSON 中保存为两位小数字符串或 `null`。

汇总行首次创建后保留原快照；基础品规以后改名、改价、停用不会改变历史批次数量和展示。歧义解决使用原事件候选快照中的包装参数，即使候选品规之后被停用，仍可完成该次历史歧义处理。

## 4. 识别与数量规则

扫码输入去除首尾空白后必须匹配 6～64 位纯数字，只查询 `is_active = true` 的品规。扫码入口与品规导入使用一致的编码长度规则。

1. 唯一匹配 `carton_code`：结果 `SUCCESS`，单位 `CARTON`，`carton_count + 1`，增加 `sticks_per_pack × packs_per_carton` 支。
2. 未匹配条码且唯一匹配 `pack_code`：结果 `SUCCESS`，单位 `PACK`，`pack_count + 1`，增加 `sticks_per_pack` 支。
3. 未匹配任何编码：结果 `UNKNOWN`，写事件但不写汇总。
4. 一个包码匹配多个启用品规：结果 `AMBIGUOUS`，保存候选快照但不写汇总。
5. 解决歧义时，所选 `product_id` 必须存在于原候选快照；追加 `RESOLVE / SUCCESS / PACK`，再更新对应汇总。
6. 同一品规通过条码和包码产生的数量合并到同一个 `scan_session_items` 行。

## 5. 幂等、事务与并发

浏览器使用 `crypto.randomUUID()` 生成 `request_id`。一次输入在获得确定业务响应前始终复用同一个请求号；只有收到成功 HTTP 响应后才为下一次扫码生成新请求号。网络失败时保留编码和请求号，允许安全重试。

每个扫码或解决请求使用一个数据库事务：

1. 使用 `SELECT ... FOR UPDATE` 锁定目标 `scan_sessions` 行；
2. 按统一数据范围校验访问权限，并校验状态为 `DRAFT`；
3. 查询 `request_id`；相同会话、事件类型和业务内容时返回原事件，并返回当前状态及 `idempotent_replay=true`；内容不同时返回 `409 IDEMPOTENCY_CONFLICT`；
4. 执行识别或校验歧义候选；
5. 成功计数时锁定已有汇总行；没有汇总行时创建；
6. 更新数量并追加事件；
7. 提交事务；
8. 查询并返回最新权威状态。

同一批次的写入由批次行锁串行化，因此不会发生汇总丢失；不同批次可以并行。`request_id` 唯一约束和 `source_event_id` 唯一约束作为最终数据库保护。

## 6. 权限规则

- `ADMIN`：可以读取和操作全部批次；
- `OPERATOR`：只能读取和操作本人分局且由非管理员账号创建的批次；
- `VIEWER`：可以读取权限范围内的批次和扫码状态，不能调用扫码或歧义解决写接口；
- 管理员创建并归属某县分局的批次，该县分局操作员和查看员仍不可见；
- 批次列表、详情、扫码状态、扫码和歧义解决复用同一数据范围条件；
- 越权和不存在统一返回 `404 SCAN_SESSION_NOT_FOUND`，不泄露记录存在性。

## 7. API 契约

### 7.1 扫码

`POST /api/v1/scan-sessions/{session_id}/scan`

```json
{
  "request_id": "d1832eb2-c4d7-4d12-9b3e-b02af02daf45",
  "code": "6901234567890"
}
```

### 7.2 解决歧义

`POST /api/v1/scan-sessions/{session_id}/resolve`

```json
{
  "request_id": "4924b13f-c1d7-4aa3-b6bb-99de240be52c",
  "event_id": 123,
  "product_id": 456
}
```

原事件必须属于同一批次、结果为 `AMBIGUOUS`、尚未解决，且所选品规必须在候选快照中。已被其他请求解决时返回 `409 AMBIGUITY_ALREADY_RESOLVED`。

### 7.3 查询扫码状态

`GET /api/v1/scan-sessions/{session_id}/scan-state`

返回结构：

```text
summary
  product_count
  carton_count
  pack_count
  total_sticks
  unknown_count
  ambiguous_count
items[]
  id, product_id, carton_count, pack_count, manual_delta_sticks,
  total_sticks, product_snapshot, updated_at
recent_events[]
  id, request_id, event_type, result, raw_code, product_id,
  unit_type, delta_sticks, source_event_id, candidate_snapshot,
  product_snapshot, operator_id, operator_name, resolved, created_at
  pending_ambiguities[]
  与事件字段一致，只包含尚未解决的 AMBIGUOUS 事件
```

扫码和解决接口返回 `event`、完整 `state` 和 `idempotent_replay`。最近流水最多返回 50 条；汇总行和未解决歧义全部返回。`unknown_count` 是该批次全部 UNKNOWN 事件数，`ambiguous_count` 是尚未解决的 AMBIGUOUS 事件数。

批次列表和详情的 `product_count`、`total_sticks` 从 `scan_session_items` 聚合，不再固定为 0。批次响应字段本身不增加或删除。

### 7.4 错误码

| 错误码 | HTTP | 条件 |
|---|---:|---|
| `BARCODE_INVALID` | 422 | 扫码编码不是 6～64 位纯数字 |
| `SCAN_SESSION_NOT_FOUND` | 404 | 批次不存在或无权访问 |
| `SCAN_SESSION_CLOSED` | 409 | 批次不是 DRAFT |
| `IDEMPOTENCY_CONFLICT` | 409 | 相同请求号对应不同业务内容 |
| `SCAN_EVENT_NOT_FOUND` | 404 | 歧义事件不存在或不属于当前批次 |
| `AMBIGUITY_ALREADY_RESOLVED` | 409 | 原歧义事件已经解决 |
| `AMBIGUITY_CANDIDATE_INVALID` | 422 | 所选品规不在原候选中 |

`UNKNOWN` 和 `AMBIGUOUS` 是正常 HTTP 200 业务结果，不作为系统错误。

## 8. 前端交互

扫码页沿用当前深绿色业务工作台风格，桌面端优先，同时保持窄屏可用：

- 顶部继续显示批次、案件信息、品规数和总支数；
- 主区域提供醒目的单行扫码框，进入页面和每次处理结束后自动聚焦；
- 仅在扫码枪发送回车、人工按回车或点击“确认识别”时提交，输入达到任何长度不得自动触发；
- 成功、未知、歧义和失败使用文字、图标和颜色共同反馈；
- 成功、未知、歧义响应后清空输入并恢复焦点；
- 网络或服务器失败时保留输入和原 `request_id`；
- 汇总表展示品规、条数、包数和总支数；
- 最近流水展示编码、识别结果、本次数量和时间；
- 待处理歧义以非阻塞卡片展示候选品规，用户可继续扫码，选择完成后恢复扫码框焦点；
- 刷新页面通过 `scan-state` 重新读取 MySQL 数据，不使用 `localStorage` 保存业务数据。

批次列表增加与品规页面一致层级的关键词搜索框、“查询”和“重置”，支持回车，始终保留 `status=DRAFT`，总数使用接口返回的 `total`。

## 10. 补充设计：回车或确认提交扫码

**批准日期：** 2026-08-31
**状态：** 已批准并实施
**优先级：** 本节覆盖本文第 4、7.1、7.4、8、9 节中关于扫码编码长度和触发方式的原有描述；品规导入与管理规则不变。

### 10.1 业务边界

- USB 扫码枪继续作为键盘设备使用，不接入厂商驱动或浏览器专用插件；
- 扫码输入框保持默认聚焦，输入过程只做数字清洗，不调用扫码 API；
- 扫码业务接受 6～64 位纯数字编码，与品规维护和 Excel 导入规则一致；
- 扫码枪自带的尾随回车、人工回车或“确认识别”按钮统一调用现有扫码 API。

### 10.2 前端状态与触发规则

1. 输入框只保留数字，最大有效长度为 64；输入达到任意长度都不自动提交。
2. 编码为 6～64 位纯数字时，Enter 和“确认识别”按钮可触发 `submitScan`。
3. 提交进行中或输入已清空时直接忽略新的提交动作，不能产生第二次请求。
4. “确认识别”按钮和 Enter 同时也是网络失败后的人工重试入口。
5. 收到 `SUCCESS`、`UNKNOWN` 或 `AMBIGUOUS` 确定响应后，清空输入、生成下一个 `request_id` 并恢复焦点。
6. 网络或服务器失败时保留编码、原 `request_id` 和焦点；使用相同编码重试时继续复用请求号。
7. 如果失败后用户修改了编码，则在下次确认提交前生成新的 `request_id`，避免旧请求号与不同编码发生幂等冲突。
8. 提交过程中禁用输入和按钮，防止连续键盘事件形成并发请求。

页面提示为“请扫描或输入条码、包码后按回车”，同时保留成功、未知、歧义和失败的中文文字反馈。

### 10.3 后端契约

`POST /api/v1/scan-sessions/{session_id}/scan` 的 `code` 必须匹配 `^[0-9]{6,64}$`。Pydantic 请求模型和业务服务执行一致校验；不满足时返回 `422 BARCODE_INVALID`，提示“编码必须为 6～64 位数字”。数据库字段长度和历史记录不调整，不执行 DDL。

识别、幂等、事务、行锁、未知记录、歧义处理和汇总规则保持不变。

### 10.4 测试与验收

- 输入和粘贴达到 13 位或其他有效长度时均不自动调用 API；
- 扫码枪尾随 Enter、人工 Enter 或点击确认各自能够触发一次提交；
- 6 位和 64 位数字可提交，5 位、65 位或非数字不形成有效扫码请求；
- 网络失败保留编码和 `request_id`，相同编码重试复用请求号，修改编码后使用新请求号；
- 后端接受 6～64 位纯数字编码，并拒绝范围外或含非数字的编码；
- 成功、未知、歧义、幂等、并发、聚焦、清空和刷新恢复的现有回归继续通过；
- 不新增数据库表或字段，不删除 17 位品规，不实现阶段 6 及以后功能，不提交或推送 Git。
