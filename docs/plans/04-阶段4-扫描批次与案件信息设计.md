# 阶段 4：扫描批次与案件信息设计

**设计日期：** 2026-08-27
**状态：** 已实施；批次可见范围与检索增强已在阶段 5 前置任务完成
**对应需求：** PRD `FR-BATCH-001` 至 `FR-BATCH-006`、SPEC `5.5` 和阶段 4 API

## 1. 目标与范围

本阶段完成“登录—新建扫描批次—填写案件信息—进入空扫码页”的纵向闭环。批次必须保存到 MySQL，列表和详情刷新后从后端重新读取。

本阶段原始范围只建设 `scan_sessions`，不建设 `scan_events`、`scan_session_items`，不实现编码识别、数量累计、异常处理、人工调整和完成批次。阶段 5 现已在不改动本阶段批次字段的前提下补充扫码表和功能。

## 2. 方案选择

采用单表保存必要批次和案件信息、展示标识实时计算的轻量方案。

- 不保存冗余的批次显示名称；
- 不建立独立案件主档、案件人员、车辆、附件或审批表；
- 不增加当事人、案由、涉案金额和执法人员列表；
- 非扫码必需信息可填写到备注；
- 品规数量和总支数不写入 `scan_sessions`，阶段 4 返回零，阶段 5 再从批次汇总表计算。

## 3. 数据模型

### 3.1 `scan_sessions`

| 字段 | MySQL 类型 | 空值 | 说明 |
|---|---|---:|---|
| `id` | `BIGINT UNSIGNED` | 否 | 自增主键 |
| `session_no` | `VARCHAR(40)` | 否 | 系统生成的唯一批次编号 |
| `business_type` | `VARCHAR(32)` | 否 | 固定业务类型 |
| `filing_case_no` | `VARCHAR(100)` | 是 | 立案编号，用户选填 |
| `location` | `VARCHAR(200)` | 是 | 检查或登记地点，用户选填 |
| `notes` | `VARCHAR(500)` | 是 | 补充说明，用户选填 |
| `branch_code` | `VARCHAR(20)` | 否 | 所属分局代码 |
| `operator_id` | `BIGINT UNSIGNED` | 否 | 创建人，外键指向 `users.id` |
| `status` | `VARCHAR(16)` | 否 | 本阶段固定为 `DRAFT` |
| `completed_at` | `DATETIME(6)` | 是 | 本阶段始终为空，为后续阶段预留 |
| `created_at` | `DATETIME(6)` | 否 | UTC 创建时间 |
| `updated_at` | `DATETIME(6)` | 否 | UTC 更新时间 |

数据库约束和索引：

- 主键：`PRIMARY KEY (id)`；
- 唯一约束：`UNIQUE (session_no)`；
- 外键：`operator_id → users.id`；
- 查询索引：`idx_scan_sessions_branch_status_created (branch_code, status, created_at)`；
- 创建人索引：`idx_scan_sessions_operator_created (operator_id, created_at)`；
- 表引擎使用 InnoDB，字符集和排序规则沿用 `utf8mb4_0900_ai_ci`。

### 3.2 枚举

业务类型只允许：

```text
MARKET_INSPECTION  市场检查
DELIVERY_CHANNEL   寄递渠道
SPECIAL_TRANSPORT  专车运输
OTHER              其他
```

API 和数据库保存稳定英文代码，前端显示中文名称。批次状态本阶段只生成 `DRAFT`，数据库约束仍兼容 SPEC 预留的 `COMPLETED`。

### 3.3 批次编号

格式为：

```text
PDyyyyMMdd-HHmmss-NNNN
```

例如 `PD20260827-163045-4821`。编号由后端按中国标准时间生成，末尾为四位随机数字；数据库唯一约束负责最终兜底，发生冲突时服务层最多重新生成三次。

### 3.4 计算展示字段

以下字段不写入 `scan_sessions`，由后端响应统一提供：

| 字段 | 说明 |
|---|---|
| `operator_name` | 创建人姓名 |
| `branch_name` | 所属分局中文名称 |
| `business_type_name` | 业务类型中文名称 |
| `status_name` | `DRAFT` 显示为“进行中” |
| `product_count` | 阶段 4 固定为 0 |
| `total_sticks` | 阶段 4 固定为 0 |
| `display_label` | 日期在前的不可编辑批次标识 |

`display_label` 格式：

```text
2026-08-27 16:30—张三—3个品规—420支卷烟
```

阶段 4 中数量部分为“0个品规—0支卷烟”；阶段 5 建立汇总数据后动态变化。前端不自行计算权威数量或拼接正式标识。

## 4. 输入与清洗规则

新建页面允许填写：

- `business_type`：必填，只能选择四个固定值；
- `filing_case_no`：选填，最长 100 个字符；
- `location`：选填，最长 200 个字符；
- `notes`：选填，最长 500 个字符；
- `branch_code`：管理员必选；操作员由后端强制使用账号所属分局。

选填文本去除首尾空白，空字符串保存为 `NULL`。请求不得提交 `session_no`、`operator_id`、`status`、数量、创建时间、更新时间或完成时间。

## 5. 权限与数据范围

| 角色 | 新建 | 列表 | 详情 |
|---|---|---|---|
| `ADMIN` | 可以，必须选择五个分局之一 | 全部分局 | 全部分局 |
| `OPERATOR` | 可以，固定为本人分局 | 本人分局 | 本人分局 |
| `VIEWER` | 不可以 | 本人分局只读 | 本人分局只读 |

操作员请求即使伪造其他 `branch_code`，后端也不得创建到其他分局。直接读取不存在或超出数据范围的批次统一返回 `SCAN_SESSION_NOT_FOUND`，不暴露其他分局数据是否存在。

县分局数据范围还必须排除管理员创建的批次：

- 管理员可查看所有创建人、所有分局的批次；
- 操作员和查看员只能查看本人分局且创建人当前角色不是 `ADMIN` 的批次；
- 管理员创建批次时即使选择某个县分局，该县分局人员也不能查看该批次；
- 列表和详情必须复用同一数据范围条件，避免通过详情地址绕过列表权限；
- 本次采用查询时关联 `users.role` 的轻量实现，不增加角色快照字段，不修改数据库结构。

## 6. API 契约

### 6.1 新建批次

`POST /api/v1/scan-sessions`

管理员请求示例：

```json
{
  "business_type": "MARKET_INSPECTION",
  "filing_case_no": "凤烟立〔2026〕001号",
  "location": "凤台县城区",
  "notes": "现场盘点",
  "branch_code": "FENGTAI"
}
```

操作员可以省略 `branch_code`；后端以当前用户分局为准。成功返回 `201` 和完整批次对象。

### 6.2 批次列表

`GET /api/v1/scan-sessions`

支持参数：

- `query`：匹配批次编号、立案编号或地点；
- `business_type`：固定业务类型；
- `status`：本阶段支持 `DRAFT`；
- `branch_code`：仅管理员可用于筛选；
- `page`：默认 1；
- `page_size`：默认 20，最大 100。

默认按 `created_at DESC, id DESC` 排序。响应包含 `items`、`total`、`page` 和 `page_size`。

批次列表页面本次只接入最小检索闭环：

- 始终请求 `status=DRAFT`，保持“进行中批次”页面定位；
- 搜索框支持批次编号、立案编号和地点的模糊检索；
- 按回车或点击“查询”执行检索；
- 点击“重置”清空关键词并重新加载；
- 总数展示使用接口返回的 `total`，不使用当前数组长度；
- 暂不增加高级筛选、分页控件和后续阶段字段。

### 6.3 批次详情

`GET /api/v1/scan-sessions/{id}`

成功返回完整批次对象。不存在或越权时返回 `404 SCAN_SESSION_NOT_FOUND`。

### 6.4 批次响应字段

```text

notes
branch_code
branch_name
operator_id
operator_name
status
status_name

updated_at
```

## 7. 错误处理

| 错误码 | HTTP | 条件 |
|---|---:|---|
| `BUSINESS_TYPE_INVALID` | 422 | 业务类型不是固定值 |
| `BRANCH_REQUIRED` | 422 | 管理员新建时未选择分局 |
| `BRANCH_INVALID` | 422 | 所属分局代码无效 |
| `SCAN_SESSION_NOT_FOUND` | 404 | 批次不存在或超出数据范围 |
| `FORBIDDEN` | 403 | 当前角色不允许新建 |
| `AUTH_REQUIRED` | 401 | 未登录或会话失效 |
| `ORIGIN_NOT_ALLOWED` | 403 | 新建请求来源不受信任 |
| `SCAN_SESSION_CREATE_FAILED` | 503 | 三次生成的批次编号均发生唯一冲突 |

批次编号三次重试后仍冲突时返回 `SCAN_SESSION_CREATE_FAILED` 和“批次创建失败，请重试”，并记录 `trace_id`，不向用户暴露数据库异常。

## 9. 数据流

```text
工作台点击新建
  → 前端读取当前用户角色和分局
  → 填写并提交表单
  → 后端校验来源、角色、业务类型和分局
  → 生成唯一批次编号
  → MySQL 写入 DRAFT 批次
  → 返回完整批次
  → 前端跳转空扫码页
  → 刷新时按 ID 重新读取 MySQL 详情
```
