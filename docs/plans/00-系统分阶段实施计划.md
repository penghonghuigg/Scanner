# 涉案卷烟智能统计系统分阶段实施计划

## 1. 实施目标

围绕一条主业务流程逐步完成数据库、后端、前端和测试闭环：

```text
登录
 → 新建扫描批次
 → 选择业务类型并填写案件信息
 → 扫描条码或包码
 → 自动识别并累计
 → 处理未识别或歧义编码
 → 核对/调整数量
 → 完成批次
 → 导出 Excel
 → 可选：一键导入简道云罚没烟登记表
```

## 2. 执行原则

1. 一次只开发一个已经获得用户批准的阶段。
2. 每个阶段按“契约 → 失败测试 → 数据库 → 后端 → 前端 → 联调 → 回归验证”完成。
3. 保持适合约 50 人使用的单体应用，不提前引入 Redis、消息队列、微服务或复杂运维平台。
4. 不使用 Alembic。`init_db` 只创建缺失表，不修改已有表。
5. 已有表需要调整时，必须先备份并提供明确 SQL，取得用户确认后人工执行。
6. 未经用户明确要求，不执行 Git 提交、推送或创建 PR。

## 3. 阶段路线

```text
阶段 1 工程环境与 Docker 基础（已完成）
  ↓
阶段 2 登录、人员注册与分局归属（已完成）
  ↓
阶段 3 卷烟品规与识别编码（已完成）
  ↓
阶段 4 扫描批次与案件信息（已完成）
  ↓
阶段 5 扫码识别、累计与异常处理
  ↓
阶段 6 数量核对、调整与完成批次
  ↓
阶段 7 Excel 导出
  ↓
阶段 8 罚没烟登记快照与简道云一键导入（可选）
  ↓
阶段 9 前后端容器化与统一验收
```

## 4. 阶段说明

### 阶段 1：工程环境与 Docker 基础（已完成）

**交付：**

- FastAPI 和 Vue 工程骨架；
- MySQL、Nginx 开发 Compose；
- MySQL 命名卷 `scanner_mysql_data`；
- 健康检查、pytest、Vitest、Playwright 和静态检查基础配置；
- Windows 本地开发启动说明。

**保持不变：** 开发期前后端本机运行，MySQL 和 Nginx 在 Docker Desktop 运行。

### 阶段 2：登录、人员注册与分局归属（已完成）

**交付：**

- 登录、当前用户和退出 API；
- HttpOnly Cookie 服务端会话；
- 管理员人员注册页面和 API；
- 田大、谢八、潘集、寿县和凤台五个分局；
- 管理员、操作员和兼容查看员角色判断；
- 登录、工作台和人员注册前端页面。

**说明：** 每人使用独立账号；同一分局允许多人同时登录。登录响应不携带权限数组，管理功能按角色判断，后续业务数据按角色和所属分局判断。

### 阶段 3：卷烟品规与识别编码（已完成）

**目标：** 建立后续扫码所需的最小基础数据。

**数据库：** 仅 `cigarette_products`。一行代表一个具体品规版本，直接保存唯一条码和可选包码；不建设 `product_codes`。

**交付：**

- 单条新增品规版本；
- 品规查询、编辑、停用和重新启用；
- Excel 模板下载、批量导入、校验和错误/警告 CSV 下载；
- 重复条码拒绝、重复包码标记歧义；
- 包码与条码冲突时导入清洗为空；
- 每条参考零售价保存及每包参考价计算；
- 管理员品规页面。

**验收：** Excel 一行对应一个版本；编码始终作为文本；`-1` 包码清洗为空；条码唯一识别；同名不同条码分别保存；重复包码可查询为多个候选；模板可下载；单条新增和批量导入均通过管理员权限保护。

**范围外：** 扫描批次和扫码计数。

### 阶段 4：扫描批次与案件信息（已完成）

**目标：** 完成“新建批次—填写案件信息—进入扫码页”的闭环。

**数据库：** `scan_sessions`。

**交付：**

- 新建、列表和详情 API；
- 市场检查、寄递渠道、专车运输和其他四种业务类型；
- 选填立案编号、选填地点、选填备注和所属分局；
- 日期在前的“日期—姓名—品规数量—总支数”动态标识；
- 唯一批次编号和 DRAFT 状态；
- 工作台快捷新建、批次表单、列表和空扫码页。

**验收：** 操作员只能操作权限范围内批次；前后端字段与 SPEC 一致；刷新页面后批次仍存在。

**范围外：** 编码识别、数量累计和完成批次。

### 阶段 5：扫码识别、累计与异常处理（已完成）

**目标：** 完成扫码枪连续扫描、自动识别和实时累计。

**数据库：** `scan_events`、`scan_session_items`。

**交付：**

- `request_id` 幂等、事务和行锁；
- 条码增加一条、包码增加一包；
- 同品规合并汇总；
- 未识别编码记录；
- 歧义包码候选选择；
- 状态查询返回权威汇总、最近流水和全部待处理歧义；
- 扫码输入聚焦，仅由扫码枪回车、人工回车或点击确认触发提交，清空恢复焦点并提供文字反馈；编码允许 6～64 位纯数字。

**验收：** 重复请求不重复计数；并发扫码不丢数量；未知和歧义在解决前不计数；服务重启后数据存在。

**实施结果：** 已完成两张表、三个扫码 API、批次权限与检索、连续扫码工作台、歧义候选处理和 MySQL 持久化验证。未识别编码本阶段只记录，不提供人工绑定；完成批次、Excel 导出和罚没烟快照继续留在后续阶段。

#### 阶段 5B：扫码盘点工作台增强（已完成）

- 四项统计卡：累计折合条数、按标准名称去重的品规数、参考零售价合计和未识别次数；
- 最近成功识别展示完整中国标准时间、名称、品牌、条码、后 6 位、条支比和当前版本价格；
- 品规数量使用单层平铺表格，每个汇总项一行；同名称不同条码平级展示价格、数量和金额；
- 支持按当前行增加或减少固定 0.1 条，或直接设置非负且最多一位小数的条数，调整不覆盖扫码条数和包数；
- 调整使用 `Decimal`、`request_id`、事务和行锁保证 0.1 条精确换算、幂等与并发安全，并追加 `ADJUST` 流水；
- 最近流水由后端按时间倒序分页，每页 10 条，显示完整时间和调整原因；
- 未新增数据库表或 DDL，继续复用 `scan_events` 和 `scan_session_items`。

#### 阶段 5D：品规删除与表格对齐（已完成）

- 品规数量统计使用标准 HTML 表格，11 列表头和内容严格居中对齐，并放大表头、内容、品规名和条码字号；
- 每个平铺品规行增加删除按钮，删除前显示包含标准品规和条码的二次确认；
- 删除仅移除当前 `scan_session_items` 实时汇总行，同时追加保留品规快照的负向 `ADJUST/SUCCESS/STICK` 流水，原扫码证据不删除；
- 删除接口使用 `request_id`、事务和行锁保证幂等；失败重试复用请求号，重新扫码可以重建汇总行；
- 只允许有写权限的用户操作 `DRAFT` 批次，不新增数据库表或 DDL；导出、CSV 和清空继续留在后续阶段。

#### 阶段 5E：品规表格单屏适配与条码高亮（已完成）

- 删除独立“条码后 6 位”列，品规数量统计缩减为 10 列；
- 完整条码继续连续显示，最后 6 位使用红色粗体突出显示；
- 保持现有字体大小，移除表格强制最小宽度和横向滚动设置，并按百分比重新分配列宽；
- 数量调整、删除确认和审计行为不变，不修改后端、数据库或 Docker 配置。

### 阶段 6+7：数量核对、来源拆分、完成批次与 Excel 导出（已实现）

**目标：** 让操作员完成更通用的数量核对并封存批次。

**交付：**

- 品规汇总最终核对；
- 固定按 0.1 条（1 包）增减或设置，并要求选择调整原因；
- 调整流水；
- 按外省流入、来源不详、市内串码、省内市外拆分品规来源；
- 来源包数与最终品规数量精确核对；
- 完成前确认；
- 批次从 DRAFT 转为 COMPLETED；
- 完成后禁止扫码和异常处理，权限范围内人员可修订最终结果；
- 已完成批次内存生成并下载四工作表 Excel，服务器不保存导出文件。

**数据库：** `scan_item_source_allocations`、`export_records`。

**验收：** 总支数不小于零；调整不覆盖原扫码流水；来源数量完全匹配；未识别和未解决歧义经二次确认后可完成；完成后不能扫码或处理歧义；Excel 与数据库最新汇总一致，编码不显示为科学计数法，文件名包含批次编号和时间。

**实施结果：** 已完成带原因的 0.1 条调整、来源目录与拆分、完成前校验和异常二次确认、四工作表 Excel 内存导出及导出审计记录；未实现服务器文件存储。

#### 阶段 6+7A：已完成盘点结果修订与导航优化（已实现）

- 左侧菜单分为“盘点作业”和“盘点结果”，管理员业务页保持完整导航；
- 作业列表只查询 `DRAFT`，结果列表只查询 `COMPLETED`；
- 已完成详情禁止扫码，可按品规名称或条码后 6 位从启用品规库加入卷烟；
- 管理员可修订全部结果，同一县分局操作员可共同修改本分局数量、来源或删除品规，查看员只读；
- 数量仍以 0.1 条为最小单位，数量与来源在事务中联合保存并追加审计流水；
- 外省流入必须选择来源省，来源市默认“不详”且可选具体城市；
- 修订后的 Excel 直接按最新数据库内容生成，不保存到服务器。

**数据库：** 不增加表或字段，复用 `scan_sessions`、`scan_session_items`、`scan_events` 和 `scan_item_source_allocations`。

### 阶段 8：罚没烟登记快照与简道云一键导入（已完成）

**目标：** 将已完成批次生成不可变登记快照，并由操作人员一键导入简道云“扫码入库清单”。

**数据库：** `integration_snapshots`。

**交付：**

- 已完成批次页面的一键导入和状态提示；
- 按标识、分局、立案编号、原登记人和最终品规汇总生成不可变 JSON；
- `PENDING`、`SUCCEEDED`、`FAILED`、`UNCERTAIN` 状态；
- 成功防重、明确失败人工重试、结果不确定时人工核查；
- 外部数据 ID、尝试次数、脱敏错误和操作人持久化；
- 后端环境变量配置和秘密脱敏。

**验收：** 同一批次只有一份快照；成功后重复点击不再次调用简道云；页面刷新和 MySQL 重启后仍显示“已导入”；条码和数量类型正确；外部失败不影响盘点结果；真实联调创建一条专门测试数据。

**范围外：** 自动推送、定时重试、批量导入、成功后覆盖外部数据、雪茄分类和复杂异步任务。

**实施结果：** 数据库建表、不可变快照、状态机、并发防重、API、前端状态交互和模拟 E2E 已完成；经明确批准后，使用专门测试批次向真实简道云接口只发送一次请求并成功创建一条登记，数据库持久化状态为 `SUCCEEDED`、尝试次数为 1。接口地址、应用 ID、表单 ID 和 API Key 仅保存在 Git 忽略的根目录 `.env` 中，`.env.example` 只保留空占位，后续正式 Compose 的 API 服务从 `.env` 注入这些配置。

### 阶段 9：前后端容器化与统一验收

**目标：** 将本机运行的前后端纳入 Docker Compose，形成可部署版本。

**交付：**

- 前后端 Dockerfile；
- Nginx、前端、后端和 MySQL 统一 Compose；
- 数据库人工备份与恢复说明；
- 健康检查、全流程 E2E 和部署验收记录。

**验收：** 一条命令启动；容器重启数据不丢失；主业务流程和权限测试通过；备份可以恢复到隔离数据库。

## 5. 每阶段固定检查

开始前：

1. 阅读技术方案、PRD、SPEC 和本计划；
2. 查看 Git 状态和上一阶段测试结果；
3. 列出对应需求、修改文件、验证命令和范围外事项；
4. 取得用户对当前阶段设计或规格的批准。

完成后：

1. 运行本阶段测试和已有回归测试；
2. 运行后端静态检查、前端静态检查和构建；
3. 检查数据库、OpenAPI 和 TypeScript 字段；
4. 验证 MySQL 数据持久化；
5. 检查秘密、调试代码、生成文件和 Git diff；
6. 报告修改文件、验证证据和未完成事项；
7. 等待用户确认，不自行提交或推送。
