# 阶段 5B：扫码盘点工作台设计

**批准日期：** 2026-08-31
**状态：** 已批准；2026-08-31 追加批准固定 0.1 条调整规格

## 1. 目标

参考 `references/prototypes/卷烟盘点系统.html`，在现有阶段 5 扫码能力上重构扫码录入页面，使操作人员能够集中查看盘点统计、连续扫码、最近识别、品规数量和扫码流水，并允许按固定 0.1 条（1 包）手工修正数量。

继续执行已经批准的扫码触发规则：输入过程不自动查询；只有扫码枪发送回车、人工按回车或点击“确认识别”时才提交。扫码编码接受 6～64 位纯数字。接口正常返回 SUCCESS、UNKNOWN 或 AMBIGUOUS 后立即清空输入并重新聚焦；网络或系统错误时保留原编码和本次 `request_id`，便于原请求重试。

## 2. 范围

本次实现：

- 盘点式扫码工作台布局；
- 四项批次统计；
- 基础库启用编码数和标准品规数；
- 最近一次成功识别详情；
- 品规数量表及固定 0.1 条数量人工调整；
- 扫码流水后端分页，每页 10 条；
- 中国标准时间完整显示；
- 已有未知编码和歧义包码处理入口。

本次不实现：完成批次、清空批次、Excel 导出、扫码流水导出和罚没烟快照。

## 4. 统计口径

### 4.1 累计扫描数量

按各品规 `total_sticks ÷ sticks_per_carton` 后求和，包含条码、包码、歧义解决和人工调整。结果为整数时显示整数条，存在零散包时最多显示一位小数。

### 4.2 已盘品规

按当前批次汇总项快照中的 `standard_name` 去重计数。同一标准名称存在多个条码版本时只计为一种品规；底层仍以 `product_id` 分别保存数量、价格快照和流水。

### 4.3 参考零售价合计

```text
单品规参考金额 = total_sticks ÷ sticks_per_carton × carton_retail_price
批次参考金额 = 所有具有参考零售价的单品规参考金额之和
```

金额显示人民币符号和两位小数。缺少参考零售价的品规不计金额，并在品规行显示“未维护价格”。

### 4.4 同名称多条码展示

品规数量表直接按批次汇总项平铺展示，每个 `product_id` 一行，不再创建标准名称组标题或条码版本子表。重复扫描同一汇总项继续累计；同一 `standard_name` 对应不同 `product_id` 或条码时显示为多条平级记录。

每行按自身品规快照计算价格、数量和金额，人工调整直接落到当前行。顶部参考零售价合计仍汇总全部行，但表格内不合并同名称行的金额。

### 4.5 未识别条码

显示当前批次结果为 `UNKNOWN` 的扫码事件数量。未知事件只记录，不计入数量。

### 4.6 基础库统计

- 启用编码数：启用品规中去重后的条码和非空包码总数；
- 标准品规数：启用品规中去重后的 `standard_name` 数量。

## 5. 最近识别

最近识别只取最近一次成功的 `SCAN` 或 `RESOLVE` 事件。未知或尚未解决的歧义事件不覆盖最近成功结果。

展示字段：

- 识别时间：按 `Asia/Shanghai` 显示为 `yyyy/MM/dd HH:mm:ss`；
- 标准卷烟名称；
- 品牌；
- 卷烟类型：固定显示“卷烟”；
- 卷烟条码：品规快照中的 `carton_code`；
- 条码后 6 位；
- 条支比：`sticks_per_carton` 支/条；
- 零售价：品规快照中的每条参考零售价，标签动态显示对应支数。

没有成功识别记录时显示明确空状态。

## 6. 人工调整

### 6.1 数据规则

- `carton_count` 始终保存扫码枪成功识别的原始条数，不直接覆盖；
- `pack_count` 保存包码成功识别数量，人工修改条数时保持不变；
- `manual_delta_sticks` 保存人工 0.1 条调整对应的支数；固定换算为 `0.1 条 = 1 包 = 20 支`；
- 最终条数为 `carton_count + manual_delta_sticks ÷ sticks_per_carton`；
- 最终条数必须大于等于 0，且最多保留一位小数；
- `total_sticks` 继续包含条、包和人工调整，是批次数量及金额的权威值。

### 6.2 交互规则

- “−”每次减少 0.1 条，最终条数为 0 时禁用；
- “+”每次增加 0.1 条；
- 数字输入框步长为 0.1，只允许非负且最多一位小数的目标条数，按回车或点击行内确认保存；
- 请求进行中禁用该行调整控件；
- 成功后使用后端返回的最新状态刷新页面；
- 失败时恢复后端权威值并显示中文错误信息。

### 6.3 调整流水

每次有效调整向 `scan_events` 追加一条 `ADJUST` 事件，自动记录数量变化、操作人和 UTC 时间。原因采用“人工调整条数：增加 0.1 条（1 包）”“人工调整条数：减少 0.1 条（1 包）”或“人工调整条数：设为 1.5 条”等稳定文字。调整不能覆盖或删除原扫码流水。

## 7. API 契约

### 7.1 按 0.1 条修改数量

```http
POST /api/v1/scan-sessions/{session_id}/items/{product_id}/carton-quantity
```

请求使用统一的 `operation + quantity` 结构。加减按钮发送相对变化，避免多人同时操作时丢失增量：

```json
{
  "request_id": "UUID",
  "operation": "DELTA",
  "quantity": 0.1
}
```

直接输入目标条数时发送：

```json
{
  "request_id": "UUID",
  "operation": "SET",
  "quantity": 1.5
}
```

响应沿用扫码操作结构，返回本次 `ADJUST` 事件和最新 `ScanStateResponse`。

后端使用十进制定点数处理 `quantity`，不使用二进制浮点数参与支数换算。`quantity` 必须是 0.1 的整数倍且最多一位小数；`DELTA` 不得为 0，`SET` 不得小于 0。每 0.1 条严格换算为 20 支，因此数据库继续只保存整数支数，无需修改表结构。

后端在一个事务中锁定批次和汇总行，校验数据范围和 `DRAFT` 状态，再计算目标条数及本次 `delta_sticks`。调整后条数不得小于 0。并发 `DELTA` 在行锁内根据最新值累计；并发 `SET` 按事务实际执行顺序以后执行值为准。唯一 `request_id` 保证重复请求不重复调整；同一请求号用于不同操作内容时返回 `IDEMPOTENCY_CONFLICT`。

调整事件的 `reason` 使用可比对的中文内容记录操作，例如“人工调整条数：增加 0.1 条（1 包）”或“人工调整条数：设为 1.5 条”，用于审计和幂等内容冲突校验。事件响应增加 `reason` 字段供流水展示。

### 7.2 流水分页

```http
GET /api/v1/scan-sessions/{session_id}/events?page=1&page_size=10
```

`page_size` 在本页面固定为 10。响应字段：

```json
{
  "items": [],
  "total": 36,
  "page": 1,
  "page_size": 10
}
```

事件按 `created_at DESC, id DESC` 排序。翻页时从后端查询，不依赖前端截取最近 50 条。

### 7.3 扫码状态扩展

`ScanStateResponse` 增加：

```json
{
  "catalog_summary": {
    "active_code_count": 41,
    "active_standard_product_count": 39
  },
  "latest_successful_event": null
}
```

`latest_successful_event` 为最近成功 `SCAN` 或 `RESOLVE` 事件；没有时为 `null`。Pydantic、OpenAPI、TypeScript 和实际响应字段必须一致。

## 8. 权限与错误处理

- `ADMIN` 可以调整其可访问的所有批次；
- `OPERATOR` 只能调整本分局且由非管理员创建的可操作批次；
- `VIEWER` 只读；
- 非 `DRAFT` 批次不能调整；
- 目标条数小于 0 返回 `422 NEGATIVE_QUANTITY`；
- 批次或品规汇总不存在，按现有数据范围规则返回 404；
- 网络失败时允许使用同一 `request_id` 重试；
- 错误响应不暴露内部堆栈并包含 `trace_id`。
