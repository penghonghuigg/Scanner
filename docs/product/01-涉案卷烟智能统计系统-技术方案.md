# 涉案卷烟智能统计系统技术方案

## 1. 项目定位

本系统是供约 50 名内部工作人员使用的轻量 Web 应用。核心目标是用扫码枪扫描卷烟条码或包码，自动识别品规、累计数量，并按固定格式导出 Excel。

系统运行在单位内网。前后端开发阶段在 Windows 本机运行，MySQL 和 Nginx 运行在 Docker Desktop；功能稳定后，再将前后端一起容器化并纳入统一 Docker Compose。

## 2. 主业务流程

```text
登录
 → 新建扫描批次
 → 选择业务类型并填写案件信息
 → 扫描条码或包码
 → 自动识别并累计
 → 处理未识别或歧义编码
 → 核对/调整数量
 → 完成批次
 → 导出 Excel
 → 可选：生成罚没烟系统推送快照
```

一次扫描批次是数据统计、完成、导出和生成快照的业务边界。

## 3. 本期范围

- 用户登录、退出、人员注册和所属分局；
- 卷烟品规与条码、包码基础数据；
- 扫描批次和案件信息；
- 条码、包码识别及数量累计；
- 未识别和歧义编码处理；
- 数量核对、人工调整和批次完成；
- Excel 汇总和明细导出；
- 已完成批次的罚没烟登记 JSON 快照；
- MySQL 数据持久化和最终 Docker Compose 部署。

本期不建设完整仓储系统、审批流、电子签章、移动 App，也不对接真实罚没烟接口。真实接口地址、鉴权和字段规范明确后再单独实施。

## 4. 技术架构

```text
USB 扫码枪（键盘输入）
          ↓
Vue 3 + TypeScript + Element Plus
          ↓  /api/v1
Nginx 反向代理
          ↓
FastAPI + SQLAlchemy
          ↓
MySQL 8.x（命名卷持久化）
```

| 层级 | 技术 |
|---|---|
| 前端 | Vue 3、TypeScript、Vite、Element Plus、Pinia、Vue Router |
| 后端 | Python 3.12、FastAPI、Pydantic、SQLAlchemy 2.x |
| 数据库 | MySQL 8.x、InnoDB、utf8mb4 |
| Excel | openpyxl |
| 网关 | Nginx |
| 部署 | Docker Desktop、Docker Compose |
| 测试 | pytest、Vitest、Playwright |

系统不引入 Redis、消息队列、微服务、Kubernetes 和数据库迁移框架。

## 5. 数据库方案

### 5.1 必要数据表

| 数据表 | 用途 |
|---|---|
| `users` | 用户、角色、所属分局和状态 |
| `user_sessions` | 服务端登录会话 |
| `cigarette_products` | 卷烟品规版本、唯一条码、可选包码、价格和包装换算信息 |
| `scan_sessions` | 扫描批次、业务类型和案件信息 |
| `scan_events` | 每次扫码、异常处理和人工调整流水 |
| `scan_session_items` | 批次内按品规汇总的数量 |
| `export_records` | Excel 导出记录 |
| `integration_snapshots` | 可选的罚没烟登记 JSON 快照 |

不单独建设导入批次、导入错误、通用审计、接口重试和接口日志表。品规导入错误直接在导入结果中返回；关键扫码和调整历史由 `scan_events` 保存。

### 5.2 数据规则

- 条码、包码、立案编号和批次编号按字符串保存；
- 金额使用 `DECIMAL`；
- 时间在数据库保存 UTC，前端按中国标准时间显示；
- `cigarette_products` 一行代表一个具体品规版本，同名但条码不同的版本分别保存；
- 每个版本只有一个全局唯一条码和零个或一个包码，不建设独立编码表；
- 包码允许对应多个品规，扫码时进入歧义处理；
- 包码与任意条码冲突时导入清洗为空，手工录入或编辑时拒绝保存；
- 数据库只保存每条参考零售价，每包参考价由后端按每条包数计算；
- `scan_events` 只追加，不提供物理删除；
- 扫码请求使用 `request_id` 唯一约束保证重复请求不重复计数；
- 批次汇总保存品规快照，基础数据后续改名或改价不影响历史批次。

扫描批次只保存最小案件信息：业务类型、选填立案编号、选填地点、选填备注、所属分局和创建人。业务类型固定为市场检查、寄递渠道、专车运输和其他。管理员可以选择并查看全部分局；操作员和查看员只能查看本人分局且由非管理员账号创建的批次，管理员代录并归属县分局的批次不会向该县分局账号开放。

### 5.3 初始化与结构调整

系统不使用 Alembic。显式执行 `init_db`，只创建当前代码中缺失的表，不删除、不重建、不自动修改已有表。

已有表需要增加或调整字段时，必须先备份数据库，列出明确 SQL，取得用户确认后人工执行。应用启动过程不执行 DDL。

## 6. 后端设计

后端按简单业务模块组织：

- `auth`：登录、退出、会话和角色校验；
- `users`：管理员注册工作人员；
- `catalog`：品规版本、条码、包码、价格、Excel 模板和导入；
- `scanning`：批次、扫码、异常、调整和完成；
- `exports`：生成 Excel；
- `integrations`：生成罚没烟登记快照。

API 使用 `/api/v1` 前缀。控制器负责 HTTP 入参与响应，业务规则放在服务层，数据库读写通过 SQLAlchemy 完成。

扫码写入在一个事务中完成：校验 `request_id`、锁定进行中批次、识别编码、更新汇总、追加流水并提交。同一批次依靠行锁串行化，`request_id` 唯一约束避免重试重复计数。歧义包码保留原 `AMBIGUOUS` 事件，选择候选后追加 `RESOLVE` 事件并以唯一 `source_event_id` 保证最多解决一次；未识别编码只记录，本阶段不允许人工绑定品规。后端返回的汇总是权威结果，前端不自行维护正式库存。

## 7. 前端设计

主要页面包括：

- 登录页；
- 工作台；
- 人员注册页；
- 新建扫描批次页；
- 扫码与实时统计页；
- 批次列表和详情页；
- 品规管理页，包括单条新增、查询、编辑、停用、模板下载和 Excel 批量导入；
- Excel 导出入口；
- 罚没烟快照查看页。

扫码页优先适配作为键盘设备的 USB 扫码枪：输入框默认聚焦，只保留数字，输入达到 13 位后立即自动提交，不等待扫码枪尾随回车；回车和按钮只作为网络失败后的同码重试入口。确定响应后清空并恢复焦点，成功、未识别、歧义和失败均提供文字反馈，不能只依靠颜色。扫码 API 只接受 13 位编码；数据库中已有 17 位品规保留但不参与扫码，品规维护和 Excel 导入仍沿用 6～64 位规则。

## 8. 角色与数据范围

- `ADMIN`：人员注册、品规维护及全部业务操作；
- `OPERATOR`：创建和操作本人所属分局的扫描批次、导出和生成快照；
- `VIEWER`：仅为现有数据兼容保留，暂不提供注册入口。

系统不维护独立的权限字符串列表，也不向前端返回 `permissions` 数组。前端只根据角色控制管理页面入口；后端对每个写接口直接校验角色和所属分局，后端结果是最终权限判断。

同一分局允许多人使用各自账号同时登录和扫码。保留服务端 Cookie 会话、请求来源校验和 `trace_id`，不为简化而降低基本安全边界。

## 9. Excel 导出

已完成批次可以导出 `.xlsx`，默认包含：

1. 批次信息；
2. 品规汇总；
3. 扫码与调整流水；
4. 未识别和歧义编码。

编码列使用文本格式，数量使用整数，金额保留两位小数。文件名包含批次编号和导出时间。

## 10. 罚没烟系统预留

本期只提供手动生成快照：操作员在批次完成后点击生成，后端将当时的批次、案件、单位、操作人和品规数量写成不可变 JSON 数据并保存。

本期不自动推送、不重试、不调用真实外部地址。未来取得罚没烟接口规范后，以快照为输入增加独立适配器，不能反向影响本地扫描结果。

## 11. 部署与持久化

开发期：

- MySQL 和 Nginx 在 Docker Desktop 中运行；
- FastAPI 和 Vue 在 Windows 本机运行；
- 浏览器统一访问 `http://localhost:8080`。

MySQL 使用固定命名卷 `scanner_mysql_data`。普通重启和 `docker compose down` 不删除数据，禁止使用 `docker compose down -v` 清理正式数据。

项目完成后补充前后端 Dockerfile，将 Nginx、前端、后端和 MySQL 纳入统一 Compose。备份先采用明确的人工命令和恢复说明，不单独引入定时备份容器。

## 12. 质量目标

- 唯一有效编码识别准确率为 100%；
- 相同 `request_id` 重复提交不重复计数；
- 浏览器或服务重启后已提交数据不丢失；
- 已完成批次不能继续扫码；
- Excel 数据与页面和数据库汇总一致；
- 前后端字段命名与 SPEC 一致；
- 真实罚没烟接口默认不存在且不会发生外发。
